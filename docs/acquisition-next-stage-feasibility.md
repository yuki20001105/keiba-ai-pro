# 追加高速化の実現可能性調査

作成日: 2026-09-14 JST。観測: 2026-09-13 23:41〜23:56 JST。
状態: 読み取り専用の調査完了。最適化の追加実装・ベンチマークは未実施。

## 結論

既存の出走JSONにある血統・過去成績を取得処理へ再利用する余地が確認できた。ただし、今回の標本で馬関連の通信を全部なくしても、通信回数の削減倍率は約4.4倍。現状から全体10倍の達成予測はできない。

改善対象は「同じURLを繰り返し取得すること」だけではなく、「別の保存先に既にある情報を、別URLから取得し直すこと」。既存HTTP・解析キャッシュの効果と二重計上しない。

今回取得した馬IDを索引検索し、バッチ開始前に保存された出走JSONだけと照合した。今回の取得で増えたキャッシュを「元から再利用できた情報」とは数えていない。

血統専用キャッシュの284頭の更新時刻は、全件が今回の観測開始以後だった。旧JSONの血統が専用キャッシュへ再利用されていないことが具体的な改善点となる。

血統の不一致には、旧値に英語名・生産国が連結され、今回の値は日本語名だけという表記差がある。全件を同一と扱うことはできず、父母の識別子・検証済み名称正規化・出典・競合検知が必要。125頭の一致も事後の照合結果であり、そのまま全出力品質の一致や実測高速化を意味しない。

過去成績は「保存時刻がバッチ開始前」「source_dateが対象馬の最も早い取得対象日より前」「着順>0、タイム非空、距離>0」で確認した。対象日は2016-02-06〜2016-12-17。12,012行を馬ID索引で読み、この対象限定集計のDB処理は約0.30秒だった。この時間は馬情報再利用機能のベンチマークではない。

過去記録があることと、真の直前走・全履歴が揃っていることは別。23:53時点の保存レース数は2019年48、2020年449、2021年61、2022〜2023年0、2024年489と疎な期間がある。JRA/NAR混在の保存件数で、開催総数や網羅率ではない。208/210をそのまま通信削減率にしてはいけない。

## 4. 倍率の条件付き上限

以下は通信回数だけの計算であり、実装後の全体時間の予測ではない。計算は `639 / (639 - 省略件数)`。

| 仮定 | 残る通信 | 通信回数の削減倍率 |
| --- | ---: | ---: |
| 完全一致を確認した血統125件を省略 | 514 | 約1.24倍 |
| 血統284件をすべて省略 | 355 | 約1.80倍 |
| 馬成績210件をすべて省略 | 429 | 約1.49倍 |
| 血統・馬成績494件をすべて省略 | 145 | 約4.41倍 |

10分の1の通信回数にするには63回以下が必要。馬関連494件をすべて省略する極端な仮定でも、さらに一覧・カレンダー109件のうち82件以上の省略が必要になる。5分の1でも、馬関連全省略に加えて18件以上の省略が必要。

解析・保存・品質検査の時間は残る。最低1秒の通信制御も、外部サービスが保証した安全速度ではなくアプリの設定である。間隔短縮や制限発生点を探る試験は行っていない。

## 5. 次に実装する順番

1. **種別別の計測を追加**。ジョブIDに紐づく実通信・再試行・実際のキャッシュ利用を月別結果へ保存。厳密な重複計測にはURLハッシュと開始終了時刻を追記式で記録する。
2. **血統・安定属性を馬ID単位で再利用**。既存JSONから必要な項目を取り出し、出典・正規化版・競合状態を持つ。曖昧、不足、訂正がある場合は再取得へ戻す。現在の所属・通算成績など時点で変わる情報は不変属性に混ぜない。
3. **対象日より前の成績をDBから生成**。学習側の既存point-in-time生成を再利用し、同日・未来を除外。履歴の網羅性が足りなければ欠損・不足理由を残し、補完取得へ戻す。現在の馬ページの最新成績で過去の前走を埋めない。
4. **確定済み期間のレース一覧を再利用**。開催台帳・期待レース数・品質検査と一体で保存する。現在の月別モバイル一覧はJRA限定なので、NARを落として通信削減を達成した扱いにしない。当日・直近は再確認する。
5. **残った解析・保存を計測して並列化**。通信上限を共有したまま、少数レースの先行解析と単一DB書き込みを検討。キャンセル・lease・途中保存の整合性を維持する。

2倍は第1検証目標、5倍・10倍は段階的な挑戦目標。いずれも今回の達成予測ではない。

## 6. 品質・検証条件

- 同じ期間・同じ初期DB/キャッシュ・同じ取得範囲で比較する。先行試験のキャッシュを後続試験だけに渡さない。
- 全体の開始〜最終品質監査完了と、馬情報再利用部分の時間を別に報告する。
- 出力項目、欠損、レース・馬件数、品質判定、学習対象、対象日以前の履歴条件を比較する。意味を変える場合は単なる同品質高速化とは区別する。
- 今回の12ヶ月は処理が完了しているが、2月・4月にそれぞれ不足レース1件、`quality_complete=false` の記録がある。「全月の品質合格」や新旧の同品質比較完了ではない。
- 過去のローカル再生9.10倍は通信・一覧・本番DBを除く別試験。この調査の全体速度と混ぜない。

## 7. 調査方法と実装箇所

SQLiteは `mode=ro`、HTTPメタデータは `idx_http_cache_freshness` のカバーリング索引で本文を読まずに確認。出走JSONは `json_extract(data,'$.horse_id')` の索引で対象284頭に限定した。全JSON集計は重い走査になるため2〜3秒で中止し、対象限定方式に変更した。

- `python-api/scraping/horse.py`: 専用血統SQLite参照、馬解析の完全性判定、6時間の解析キャッシュ。
- `python-api/scraping/storage.py`: 出走JSON保存。
- `keiba/keiba_ai/point_in_time_history.py`: 厳密な過去日だけを使う履歴生成。
- `python-api/scraping/fetch_pipeline.py`: 実通信総数、最新状態型のHTTPキャッシュ・再開台帳。
- `python-api/scraping/race_list.py`: 日別取得とJRA月別フォールバック。
- `python-api/scraping/jobs.py` / `server_batch.py`: 月別実行結果、期間バッチ、時間集計。

`resume_hits` はキャッシュ期限切れで再通信する場合も含むため通信削減数には使わない。`rate_wait_ms` は並列タスクの待機合計なので経過時間と合算しない。速度制御サンプルはリセットされるため累積通信履歴には使わない。

この調査では実行中ジョブ、DB、通信間隔、アプリケーションコードを変更せず、外部への追加取得・再起動・停止も行っていない。変更は本調査メモの追加のみ。
