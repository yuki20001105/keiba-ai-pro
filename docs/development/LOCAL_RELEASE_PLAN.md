# 競馬AI ローカル版リリース計画

最初のリリース先はユーザー確認済みのローカル版とする。まず現在のPCで安全に使える版を完成させる。動作保証、モデルの予測精度、買い目の収益性は別の合格条件とする。公開配信は既存の本番承認手順を維持し、この計画だけでは開始しない。

最短経路は、既存の研究と高速化を再利用し、認可・進捗監視・説明の誤表示を修正してから、5機能の回帰検証を一括実行すること。利益が確認できるまで無制限にモデル探索を繰り返す方針は採らない。

## 実施順序

| 順序 | 作業 | 完了条件 |
| --- | --- | --- |
| 1 | 安全性と重要なUI不具合の修正 | 認可matrix全経路分類、旧応答の表示禁止、通信失敗でジョブIDを失わない |
| 2 | 5機能の動作検証 | 単体テスト・API契約・ブラウザーfixture・本番ビルドが通過 |
| 3 | 高速化の反映 | APIが実行枠を公開し、画面がその上限に従う。停止中の処理を巻き込まない |
| 4 | 現行モデルの評価整理 | モデルID・特徴量・検証期間を結び付け、研究候補の数値と混同しない |
| 5 | 前向き成績の検証 | 発走前入力・オッズ、見送り・失敗母数、公式精算、校正と回収率を別集計 |
| 6 | ローカル版の最終操作確認 | 実環境で取得・学習・予測・成績・管理の一巡と復旧を確認。未完了ゲートを残さない |

1〜3は並行作業し、4は保存済み研究を監査して開始する。5の未知期間データは時間が必要なので、基本機能の完成と切り離して蓄積する。

現行速度モデルは116列の列名・順序がboosterまで一致し、保存時と実行時のsklearnも1.9.1で一致した。未来項目・ID項目の交差は0件だった。ただし2026年10月10日東京1Rでは29列、2026年1月12日京都1Rでは40列が未計算だった。欠落数はレースごとに異なり、以前の41列という報告は今回再現していない。

学習時の特徴量ソースは保存ハッシュと一致する候補コミットを特定したが、現行ソースとは異なる。学習時・現行双方の会場コード生成が開催日番号を使用している問題もある。既存モデルだけの入力を変更すると学習時との対応が崩れるため、正式な意味へ修正した別の移行候補で再評価する。旧外部API由来のholding16列をDB最速値で代用しない。

未来11,376行・同日102行を履歴から除いた過去標本でも入力値・スコアは厳密一致した。ただしこれは旧profile・外部指数の観測時刻の証明ではない。列一致・有限な予測値・並列再現は学習時の入力と実運用入力の同等性や利益適性を証明しない。監査結論は`NOT_SEMANTICALLY_VERIFIED`で、正式な利益モデルへの昇格は保留する。

予測APIは未計算列・禁止列・履歴読込失敗・ソースハッシュの差を返し、画面は短い「参考予測」と折り畳み詳細で示す。入力の意味の同等性と校正が未検証なら買い目を見送る。`value-selection-v2`へ版を更新し、診断のない旧キャッシュや旧snapshotから新規購入済み記録を作れないようにする。既存の保存済み成績は削除しない。

## 確率と回収率

順位スコアを勝率とみなさない。確率を使う候補はNLL・Brier・購入対象の校正誤差を市場基準と比較し、開催日単位の対応bootstrapと多重比較を考慮した区間を付ける。

回収率は払戻額÷投資額×100とし、精算済みの同じ買い目だけで計算する。仮想成績、購入済み成績、歴史データ研究を混ぜない。未精算、見送り、投資0円は回収率0%ではなく未定義として扱う。

既存の固定単勝Top1研究では2022年2,934レースのH04回収率73.88%、95%参考区間68.53〜79.34%。市場基準は82.06%。これは結果ページの歴史オッズによる参考値で、発走前5分の実行可能オッズを再現した値ではない。非単勝は全組合せの事前オッズ不足によりROI未評価。100%超は未達で、買い目変更だけで解消できると仮定しない。

次は固定時刻の入力と券種別オッズを保存し、固定買い目ルールで前向き評価する。発走前に記録が間に合わなかったレース、入力不足、取得失敗、見送りも母数に含める。利益の昇格条件は既存の本番モデル承認契約を緩めず、独立した未知期間・十分な母数・市場比較・校正・回収率区間で判定する。回収率100%を保証する表示はしない。

## 前向き証跡の復旧方針

凍結したTrack A集計には、JSON保存時の順位辞書キーが整数から文字列に変わり、ハッシュ照合に失敗する問題がある。読み取り専用の限定監査では91件がキー型だけの復元で元のハッシュへ完全一致した。

これは既存集計の合格やガード解除ではない。元のDB・イベント・ハッシュ・凍結ソースは変更しない。不明な差を許容する一般的な正規化はしない。

別バージョンの読み取り専用集計`report_forward_paper_compatible.py`を実装した。2026年10月10日15:40 JSTの一貫した読取トランザクションで92,906イベント・138レース・90予定日、35凍結ソース・4成果物、106捕捉／精算再演算が合格した。92件だけが整数順位キーの復元により元ハッシュへ完全一致し、それ以外の変更は許容しない。旧strict guardのFAILはレポートに残す。

## 高速化と計測

CPU計算は最大4プロセス、各モデルの内部スレッドを抑えて競合を避ける。RAM不足時は枠を減らし、画面はAPIが公開する枠数に従う。GPU非対応の導入済みLightGBMを前提にCPU最適化を先行し、GPU導入をリリース条件にしない。

保存済み4レースの同一入力・同一予測・同一SHAP比較では、履歴SQL＋特徴量＋推論＋説明が306.03秒から18.01秒へ短縮した。約17倍はこのCPU経路のみで、外部取得・全24レース・UIの全体時間の倍率ではない。

追加計測は、全体経過、HTTP・減速待機、DB、特徴量、推論、説明、CPU待機、成績保存を分離する。P50/P95、冷起動と再利用、成功率、品質一致を同条件で比較する。外部HTTPは全体レート制限・Retry-After・減速を維持し、保存済み情報の再利用による通信削減を優先する。

## シンプルなUI

主導線は5機能だけとする。通常画面は「何をするか」「現在の状態」「結果」「次の操作」を中心にし、ジョブID・モデルID・詳細指標・技術ログは詳細へ置く。

取得と予測には完了数・経過時間・実測速度・残り時間を表示し、計測前の推定は断定しない。モデル画面は順位相関とRMSEを主に見せ、補助指標は検証期間と一緒に表示する。説明は同じ予測のSHAPを再利用し、LLMは要求時だけ生成する。成績は仮想と購入済みを別タブにする。

失敗レースだけの再試行、横長予測表の主要項目への絞り込み、モデル名の短い識別子は後続改善とし、認可・時点保証・成績分離より先に大規模画面改修はしない。

## 安全な候補モデルの接続

旧116列の不足を別の意味の値で埋めず、既存の市場情報を使わない研究候補を別経路へ接続する。最初は基本16列のM01と、基本と対象日より前の履歴47列のM02だけを対象にする。旧holding16列、後日のprofile、時点未保証のSpeed Figure・調教、対象レースの結果、オッズ・人気は入力しない。

`experiments/dataset.py`の中央平地・完全出走集団・会場一致判定と、`experiments/features.py`の対象日より前だけの履歴生成を再利用する。会場は保存値と`race_id[4:6]`の一致を検証する。`forward_adapters/feature_state.py`の当日入力生成は歴史pipelineとの一致テストを再利用できるが、凍結したH04専用推論は変更せず、新しい候補用adapterを分離する。

既存保存済みのM01・M02成果物は元ハッシュを照合して、列・値・カテゴリ・推論・SHAPの互換smokeに使用する。これは新たなモデル採用や利益の合格ではない。通常のローカル学習をそのまま再実行しても旧特徴量生成を通るため、この入力問題の解消にはならない。

再学習が必要な場合は、別driverで2候補だけを登録し、固定seed・固定200roundでCPU2枠から実行する。対象データ・評価期間・16列／47列を開始前に固定し、再探索やOptunaは実行しない。比較はレース平均順位相関と速度RMSE（m/s）を主とし、年別・芝ダート別・履歴量別の成績と開催日単位のbootstrapを残す。既に見た2023〜2026年は事後検証と明記し、未知期間は固定した発走前入力で評価する。

候補用の入力診断を合格にするには、歴史再演算、結果項目を除いた入力、同日・未来履歴の拒否、実出馬表の正規化入力で値が一致する証拠が必要。既存の`semantic_parity_verified=false`を無条件で変更しない。入力が合格しても、確率校正と買い目の前向き評価は別条件とする。使用中モデルは自動で切り替えない。

## 検証の実行方法

通常の自動検証は次のコマンド。実取得・実学習・実購入は開始しない。

```powershell
npm run verify:release:local
npm run verify:release:local -- --build --e2e
```

本番ビルドは`build/release-check`に分離し、稼働中の`.next`を上書きしない。ブラウザー検証はloopbackの別ポートと明示したfixtureだけを使う。`npm run test:e2e`全件には実取得・Optuna学習を含むテストがあるため、リリース確認には使わない。

各実行のログ・結果・ソース指紋は`reports/generated/release-readiness`の新規ディレクトリへ保存する。途中でソースが変わった実行、未完了の実行、失敗した検証を合格とは扱わない。これはローカル自動検証であり、公開許可や収益性の合格ではない。

## 安全候補の比較と画面接続
