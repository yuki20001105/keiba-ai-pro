# ローカル並列モデル比較の運用

保存データのスナップショットから、安全な特徴量で複数モデルを比較するための実験用CLIです。候補は実験フォルダ内に保存し、使用中モデルへ自動反映しません。

## 実行手順

PowerShellでリポジトリのルートへ移動します。`$experimentRoot` の末尾は実験IDです。新しい実験では未使用のIDを指定してください。

```powershell
Set-Location 'C:\Users\yuki2\Documents\ws\keiba-ai-pro'
$experimentRoot = 'reports/generated/model-experiments/20260919-safe-comparison-01'

# 1. 元DBのスナップショットを作成し、共通の学習データを準備
& '.\python-api\.venv\Scripts\python.exe' '.\scripts\run_model_experiment.py' prepare --root $experimentRoot

# 2. CPU/GPUの実行能力を確認（任意。runでも確認されます）
& '.\python-api\.venv\Scripts\python.exe' '.\scripts\run_model_experiment.py' probe --root $experimentRoot

# 3. 実データでの小規模計測後、モデル比較を実行
& '.\python-api\.venv\Scripts\python.exe' '.\scripts\run_model_experiment.py' run --root $experimentRoot
```

`prepare` の標準取得元は `keiba/data/keiba_ultimate.db` です。別の保存DBを使う場合のみ `--source <DBのパス>` を指定します。ネット取得は行いません。

`prepare` はスナップショットと特徴量を作るため、時間とディスク容量を使います。`probe` は小さな合成データで実際に学習可否を確認します。`run` は実際のモデル学習を行います。いずれも単なる状態確認コマンドではありません。

### 進捗確認・停止

別のPowerShellで、同じ実験IDを指定します。

```powershell
$experimentRoot = 'reports/generated/model-experiments/20260919-safe-comparison-01'

& '.\python-api\.venv\Scripts\python.exe' '.\scripts\run_model_experiment.py' status --root $experimentRoot

& '.\python-api\.venv\Scripts\python.exe' '.\scripts\run_model_experiment.py' cancel --root $experimentRoot
```

この例もリポジトリルートから実行してください。`status` は実験・試行の状態をJSONで返します。各試行の `progress_stage` と `progress_pct`、または `trials/<試行ID>/progress.json` で段階別の進捗を確認できます。進捗率は残り時間の保証ではありません。

`cancel` は停止要求です。未開始の試行は取り消し、実行中の試行は確認ポイントで協調停止します。ドライバーは通常15秒待ち、それでも終了しなければ**そのドライバーが起動した子プロセスだけ**を終了・回収します。既存のWeb/Pythonサービスは停止対象にしません。

停止完了は `status` で確認してください。実験台帳作成前の `prepare`・`probe`・初期計測は、このキューの `cancel` 対象ではありません。ドライバーが終了済みの場合も、停止コマンドだけで残存プロセスの回収まで保証されるわけではありません。

## 比較する内容

| 候補 | 内容 |
|---|---|
| M01 | 速度予測・基本特徴量 |
| M02 | 速度予測・基本＋過去成績 |
| M03 | 速度予測・拡張特徴量 |
| M04 | 開発期間の比較で特徴量を厳選。改善を確認できなければM03を維持 |
| M05 | 順位予測との比較 |

履歴は対象日より前の保存データから作り直します。同日の結果・未来の結果、元の `prev_*`、オッズ・人気を予測入力として混ぜません。オッズ・人気・確定結果・払戻は、必要に応じて教師データや評価に使用します。

比較対象は品質条件を満たす中央競馬・平地のレースです。全出走馬の結果・タイムが揃った集団で評価するため、欠損を含む実運用の全レースで同じ成績が得られるという意味ではありません。

取得元で芝・ダートと誤分類された障害レースもあるため、レース名・種別・クラスの障害マーカーと保守的な距離集合を併用します。これは今回の実験の採用範囲であり、公式の全コース網羅判定ではありません。距離集合外は元DBから削除せず、実験対象から隔離します。過去成績の母集団にも同じ判定を適用します。

履歴は2013年以降の適格な保存済みレースに限られ、全キャリアの網羅性を保証しません。馬体重などレース直前の入力を含むため、この評価を前日予測の精度とはみなしません。

### 検証期間の読み方

- **2023〜2025年：開発用の時系列検証。** 各検証年より前のデータだけで学習し、特徴量処理や速度の基準値も学習側で作ります。モデル選定はこの期間で行います。
- **2026年：既知データの事後比較。** 過去の学習などで既に参照された期間です。コード上の `final` は処理段階の名前であり、未知の最終テストではありません。

候補選定を保存した後に、基準候補と選定候補だけを2026年で比較します。2026年の成績や回収率を見て候補を選び直す設計ではありません。

主な指標は順位相関、RMSE、予測1位の勝率、人気1位との差、回収率です。順位モデルと速度回帰モデルでは出力の意味が異なるため、指標が適用できない場合は無理に数値化しません。

回収率は予測1位へ単勝100円を固定したシミュレーションです。払戻不明を0円に置き換えず、全体の回収率を未計測にします。人気との比較は記録された最終人気による参考比較です。購入・利益を保証する評価ではありません。

## 並列化と安全制御

- 共通のOSファイルロックで、別の実験フォルダを指定したドライバーの同時起動を抑止します。別フォルダに未解決の実験台帳がある場合も開始を拒否します。
- 各実験台帳のlease・バージョン・fencing tokenで所有者を確認し、同じ試行の二重実行や古いワーカーによる結果確定を防ぎます。
- 元DB・データセット・定義・コード・使用中モデルの契約をハッシュで固定します。途中で変更された場合は停止し、異なる条件の結果を混ぜません。
- ワーカーごとに出力先とログを分けます。結果が確定するまで、生成途中のファイルを成功結果として扱いません。
- 実データの初期計測から必要メモリを見積もり、空きメモリを残して実行枠を決めます。現行の自動構成はCPU 1〜2枠、またはCPU 1枠＋GPU 1枠です。CPU側は1ワーカー4スレッドです。
- 実行中の試行がなく、資源不足で開始できない状態が5分続くと明示エラーにします。正常に進行している長時間学習を5分で打ち切る制限ではありません。

GPUを搭載しているだけでは使用しません。`probe` で対応ビルド・デバイス・有限な予測値を確認し、さらに開発用の実データ計測でGPU学習がCPUより速いことを確認した場合だけ採用します。この短い計測での学習速度と、準備・評価・保存を含む実験全体の速度は別です。GPUを使うために稼働中のPython環境を自動で入れ替える処理はありません。

## 出力の場所

出力先は `reports/generated/model-experiments/<実験ID>/` 配下に限定されます。

```text
<実験ID>/
  snapshot.json                    元DBスナップショットの参照・ハッシュ
  snapshots/                       元DBから作った独立スナップショット
  dataset/
    dataset.parquet                共通の整理済み学習・評価データ
    dataset_manifest.json          特徴量・品質判定・期間・ハッシュ
  capability.json                  CPU/GPU能力確認
  pilot.json / pilot.log            実データ初期計測
  contract.json                    固定した実行・データ・資源条件
  experiment.sqlite3               試行状態・lease・結果の台帳
  logs/                            この実験のワーカーログ
  trials/<試行ID>/
    process.json / progress.json   プロセス識別・進捗
    artifacts/                     学習モデル・予測値・寄与の情報
    result.json                    確定前候補を含む出力。成功は台帳で確認
    artifact_manifest.json         ファイルごとのハッシュ
    failure.json                   失敗時の情報
  selection.json                   開発期間で確定した選定
  comparison.md / comparison.json  完了後の比較結果
```

`snapshots/` の内容、候補モデル、台帳を既存のDBや `python-api/models/` に上書きコピーしないでください。候補を実際の予測へ採用するには、別途、推論互換性と評価結果を確認する作業が必要です。このCLIはモデル登録・既定モデル変更・購入を行いません。

## 失敗・停止後の扱い

| 状態 | 意味・対応 |
|---|---|
| `queued` | 開始待ち。資源と実行枠を確認 |
| `running` | leaseを持つワーカーが実行中 |
| `cancelling` | 停止要求済み。終了確認を待つ |
| `completed` | 結果を台帳へ確定済み |
| `cancelled` | 未開始の取消、または実行停止を確認済み |
| `failed` | 失敗を記録。`failure.json`・ログを確認 |
| `unknown` / 実験の `blocked` | lease期限切れなどで安全に終了を確認できない。調査が必要 |

`unknown` を自動で `queued` に戻す処理はありません。期限が切れても、元のワーカーがまだ動いている可能性があるためです。

同じIDの失敗・不明な試行を、そのまま再実行する操作には対応していません。原因、残存ワーカー、台帳、成果物を確認したうえで再試行方針を決め、新しい実験IDを使用します。ただし、**新IDだけで未解決の旧実験を迂回することはできません**。旧実験が `active`・`cancelling`・`blocked` のままなら先に調査・解決が必要です。

ロックファイルの削除、台帳の手編集、成果物の上書きで強制的に再開しないでください。完了済み結果がある正常な実験では同じ条件を確認して既存結果を利用できますが、コード・使用中モデル・データ定義を変更した場合は契約不一致として再開を拒否します。

## 実装時の確認

2026年9月19日時点で、関連テスト175件の通過を確認しています。時系列特徴量・評価・実行台帳・Windowsの実ワーカー識別と停止などの実装検証です。これはモデル精度、GPU利用可否、実データでの高速化率を保証する数値ではありません。実際の判断には実験フォルダ内の計測値と比較結果を使用してください。
