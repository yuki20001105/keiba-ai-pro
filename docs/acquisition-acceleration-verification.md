## 追加改善

- HTTP・解析・血統キャッシュのSQLite接続を上限付きで再利用。毎回の開閉・WAL初期化を削減し、各書き込みのコミットは維持する。
- HTML本文を読まずに有効期限を確認できる索引を追加。再開台帳・HTTPキャッシュの二重確認も除去する。
- 解析結果を件数・メモリ量に上限のあるキャッシュに保持。元データの更新・期限切れ・外部プロセスによる訂正は引き続き検知する。
- 馬HTMLの解析を最大2ワーカーへ移し、通信と並行して処理する。
- 全文テキスト・プロフィール・血統表を維持し、既存の馬特徴量で使用しない成績表の3走目以降の行だけをBeautifulSoupへの入力から除外。元HTML・本番データ・既存出力項目は削除しない。解析例外時は従来方式へ戻す。
- 本文と同時に読んだ・保存した更新情報を保持し、解析中に別処理が同じURLを更新しても古い結果を新しいデータとしてキャッシュしない。月別一覧にも同じ照合を適用する。

DB接続だけの途中比較は24レースで50.48秒→10.21秒（4.95倍、1試行）。全項目・欠損・品質・学習対象の判定は同一。これは最終測定ではなく、以降の複数回の結果と混在させない。

## 実取得5倍について

外部アクセスの安全な限界値は未確認。最低1秒という設定も提供元の許可値ではない。HTTP回数を増やして制限の発生点を探る試験は行っていない。

通信数が同じなら、ローカル解析の5倍改善だけでは実取得5倍にならない。今回のレース標本は新旧とも初回1,072回の再生要求が残る。実通信に置き換えた場合、新しい共有制御では開始間隔だけで最低約1,071秒を要し、応答・初期2秒間隔・バックオフの時間も加わる。

旧版はホスト別の待機判定と開始時刻の記録が非原子的で、4頭の並行処理が同時発行できた。したがって共有制御導入後は、通信主体の初回取得が以前より遅くなる場合もある。**全期間の実取得5倍は未検証・未達判定**とし、ローカル測定の倍率で代用しない。実取得で5倍を狙う次の指標は、同じ品質で実際の通信数とジョブの総所要時間が減ったかどうかである。

## 比較条件

- 実際に保存されている同一の HTML を固定して再生する。netkeiba への追加アクセスはしない。
- 変更前・変更後の HTTP キャッシュ、血統キャッシュ、解析キャッシュは一時領域へ分離し、同じ初期条件で開始する。
- 各条件を3回実行し、中央値で比較する。原則交互に実行し、並行測定しない。最終レース表だけは上記の安全性修正後の別時点比較であり、参照した全試行を保存する。
- 「初回」「保存 HTML あり」「同じ処理の再実行」を分ける。
- 全出力の SHA-256、欠損件数、取得品質判定、学習対象判定が一致しない比較は高速化率を採用しない。

対象は実際に保存されていた2020年・2025年の平地24レース・377頭のレース解析＋馬情報補完と、完全な保存ページがある24頭の馬情報を3巡する部品単位の比較。前者は画面の取得ジョブと同じ `quick_mode=True`、後者は `quick_mode=False`。

| 条件 | 初期状態 |
| --- | --- |
| 初回 | HTTP・解析キャッシュなし。レース比較では既存血統9頭分を両実装へ同じ内容で投入 |
| 保存 HTML あり | 同じ成功 HTML を有効な HTTP キャッシュへ投入。解析キャッシュは空 |
| 再実行 | 各実装で同じ入力を1回処理し、その後の2回目を計測 |

このサンプルは、保存ページの有無と同じ馬の再登場を条件に選んでいる。2016〜2026年全体を代表する無作為標本ではない。馬ページが不完全なレースと、完全なプロフィールの部品比較を合算して全体倍率にはしない。

## 測定に含むもの・含まないもの

含む: HTML 解析、キャッシュの読み書き、共有通信制御のローカル処理負担、馬情報の補完処理。

結果JSONの `html_parse_count`・`html_parse_wall_sec` はBeautifulSoup呼び出しだけの補助指標。追加したlxml前処理の時間はこの補助指標には含まれないが、表に使う総所要時間 `local_replay_wall_sec` には含まれる。

含まない: 実ネットワークの応答時間、実際のレート待機・バックオフ、日付一覧の取得、デスクトップレースURLからの切替、本番 DB への保存、画面操作と月間ジョブ全体。

したがって、ここでの倍率は **ローカル再生処理の倍率**。実際に11年間のデータを取得する所要時間の倍率ではない。共有通信制御で以前の過剰な同時送信を抑える分、初回の実取得が遅くなる可能性もある。

失敗応答は保存済み台帳の HTTP 400/404/410 を再生する。台帳に本文がないため空本文とし、成功データは補作しない。モバイルの保存応答があるデスクトップ互換失敗だけは模擬400であり、結果JSONに回数を記録する。

## 品質上の注意

全項目が一致することは、すべての特徴量が取得済みという意味ではない。
この過去レース標本には血統の欠損が多い。欠損を隠さず、失敗している血統取得の再試行も維持する。不完全な馬情報を取得完了キャッシュへ昇格させない。

学習対象判定では実ローダーと同じ日付・走破秒数の別名を与え、同一の適格判定を実行する。この検証自体はモデル学習を行わず、予測精度の向上や過去時点の特徴量の正しさを立証するものではない。

## 並列処理について

既存の馬情報取得は最大4頭の非同期タスクを並行処理している。追加でHTMLの純粋な解析だけを最大2ワーカーで処理し、ネットワークや別タスクを止めないようにした。SQLite保存などは既存のスレッド処理を維持している。

外部HTTPはプロセス・サブドメイン間で同時1件に制限し、キャッシュだけのタスクにあった固定待機を除いた。解析の並列化は外部HTTPの同時送信数を増やさない。

## 再現方法

`scripts/benchmark_acquisition_replay.py` に変更前の `scraping/` ディレクトリを指定する。

```powershell
.\python-api\.venv\Scripts\python.exe scripts/benchmark_acquisition_replay.py --baseline-package <変更前のscrapingディレクトリ> --race-count 24 --repeats 3
```

馬情報の部品比較は `--workload profiles --output reports/generated/acquisition-profile-replay.json` を追加する。
レポートには固定 HTTP 入力のハッシュ、比較ソースのハッシュ、全試行の秒数・再生要求数・品質判定・欠損件数を残す。HTTP 入力ハッシュは血統の初期値や日付情報まで含むハッシュではないが、それらも全試行で同じ固定コーパスから読む。

今回と同じ固定入力を使う場合は、結果JSONの `frozen_corpus_path` を `--frozen-corpus` に渡す。再生用コーパスと変更前ソースはローカル一時領域に残しており、削除していない。`--stages cold`・`--implementation optimized` で診断範囲を限定でき、`--profile` はcProfile用（プロファイラー付き秒数は正式な倍率には採用しない）。

安全性修正後のレース表の再構成は `--current-report reports/generated/acquisition-replay-optimized-v3-raw.json --reference-baseline-report reports/generated/acquisition-replay-v2.json --output reports/generated/acquisition-replay-v3.json`。全入力・件数・各実装のソースハッシュ安定性・品質一致を検証し、不一致時は倍率を付けず失敗する。
