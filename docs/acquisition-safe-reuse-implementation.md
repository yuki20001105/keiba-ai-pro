# 品質を維持する追加取得高速化の実装

実装・検証日: 2026-09-14 JST。

## 結論と稼働反映

既存の取得画面から呼ばれるPythonの取得経路へ、種別別計測・保存血統再利用・厳密な過去履歴の監査生成・確定済み日別一覧再利用を組み込んだ。

**馬の過去成績は生成・監査まで。履歴があるだけで馬詳細HTTPを省く処理は有効化していない。** 履歴網羅性や全プロフィール項目の同等性を証明できないため、従来の馬詳細取得を維持する。10倍・5倍・全体2倍を達成したとの判定はしない。

実行中の全期間バッチを妨げないため、Pythonの停止・再起動はしていない。新コードの稼働反映は次回の安全なPython再起動後。画面側に追加操作・設定は不要で、従来の「取得開始」経路を使用する。

00:23 JST時点で既存バッチは実行中、20/129ヶ月完了、2017年9月を処理中、保存126レース・1,329頭。ローカル `/health` は `ok`。これは旧プロセスの稼働確認であり、新コードの本番動作・速度検証ではない。

## 実装内容

### 1. 通信と時間の計測

- 実通信開始・HTTP応答・成功・失敗・実際に発行した再試行・キャンセルをURL種別別に計測。
- 種別は `calendar / list / race / horse / pedigree / odds`。`by_kind_*` の整数カウンターで月別・全期間結果へ集計する。
- 実際のHTTPキャッシュ利用、本文がない再開メタデータだけのヒット、成功した重複待機を区別。
- 通信中の累積時間と待機の累積時間は、並列タスクで重なるので全体の経過時間とは合算しない。
- 完了したworker試行について、初期処理・待機・最終品質監査・完了記録までの経過を別途保存。最後の追加計測保存自体は対象外。
- 全期間バッチは最初のバッチチェックポイントから最終月の完了記録までを計時し、復旧・月間の待ち時間を含める。
- 旧バッチの途中で初めて計測を始めた場合は `batch_wall_time_complete=false` とし、全期間時間を不明扱いにする。再開後だけの時間を全期間の時間として表示しない。
- 通信カウンターはworker試行単位。中断した過去試行の未保存通信までは復元せず、親集計に `metrics_include_interrupted_attempts=false` を明記する。
- 計測ファイルや追加計測保存が失敗しても、すでに確定した取得完了を失敗・再取得対象へ変更しない。

### 2. 保存済み血統の再利用

- 取得workerだけで有効なコンテキストを追加。予測・学習・他の直接取得経路は変更しない。
- 馬ID索引で旧出走JSONを読み、父・母・母父の完全性、一貫性、SQL・JSONの馬ID／レースIDを確認。
- プレースホルダー、英語併記、国名などの曖昧表記、部分情報の競合は従来取得へ戻す。推測で名称の末尾を削らない。
- 専用血統キャッシュが完全なら従来値を優先。保存JSONの候補を無期限の専用キャッシュへ書き込まない。
- 保存元の更新・削除・競合を検出し、以前の再利用候補を使い続けない。
- 読み取りは `mode=ro`、短いスナップショット、最大1,024行・SQLite実行時間の予算0.35秒。索引がなければ全走査を行わない。
- 保存血統を注入した解析キャッシュだけを出典付きで隔離する。専用キャッシュ優先時は従来の解析キーを維持し、日付が変わるだけで同じ馬ページを再解析しない。
- 修復指定では新しいDB再利用を無効化する。従来のHTTPキャッシュ・修復処理の意味を勝手に変更して全HTTPを強制更新することはしない。

以前調べた284頭に同じ判定を当てた読み取り確認では、125頭が適格、159頭は曖昧表記としてフォールバックした。現在は専用キャッシュが既に埋まっているため、この数を今後の通信削減数として扱わない。

### 3. 対象日以前の過去成績を生成

- 必ず `source_race_date < target_race_date`。同日・未来の成績を除外。
- 保存済みの最新2走を生成し、元レースID・出典ハッシュ・欠損・競合・日付台帳の連続性を記録。
- 不明日付や未解決結果があれば網羅性は未確認。日付台帳が整合しても、海外を含めた全履歴や現在プロフィールの完全性が証明されたとは扱わない。
- `audit_only=true`、`can_replace_provider_detail=false` を維持。生成値で従来の前走・現在プロフィール・通算成績を上書きしない。
- 監査情報は `scrape_horse_reuse_audit` へ、出走データと同じトランザクションで保存。学習用の出走JSONには入れない。
- 更新時は古い監査情報も更新／除去し、書き込み失敗時は出走データとまとめてロールバックする。

したがって、今回は「DBからの安全な履歴生成と根拠保存」を実装した段階であり、馬成績ページの通信削減は未実装。学習用特徴量そのものを今回の監査情報で差し替える変更も行っていない。

### 4. 確定済みレース一覧の再利用

- 30日超の過去日、非空、全レースの品質監査成功が条件。
- 順序付きレースID、対象範囲、元レスポンスの本文ハッシュ・取得時刻、パーサー／品質ルールの版、保存データのハッシュを保存。
- 当日・直近、空一覧、品質不足、出典不明、変更・削除、修復指定では再利用しない。
- 出典の取得から30日で失効。再利用で有効期限を延長しない。
- JRA限定のモバイル／当日一覧を、中央・地方を含む全体一覧として昇格しない。
- 既存の正の日付チェックポイントが新しい一覧の有効性確認を迂回しないように統合。ただし同一ジョブの完了済み日付の途中再開チェックポイントは従来通り維持。
- 既存のレースID索引を再利用し、重複索引を追加しない。適切な索引がない旧DBだけ初回保存時に作成する。

## 品質比較と速度測定

同一コードで取得コンテキストを無効／有効にし、同じ初期HTTP・血統・保存データを用いて交互に各3回、計24回測定した。外部HTTPは0回。

| 測定対象 | 変更前の中央値 | 変更後の中央値 | 再生要求数 |
| --- | ---: | ---: | ---: |
| 血統を再利用できる6頭の馬情報処理 | 0.368秒 | 0.249秒（約1.48倍） | 12 → 6 |
| 血統名が曖昧な6頭 | 0.371秒 | 0.381秒 | 12 → 12 |
| 保存情報がない6頭 | 0.370秒 | 0.381秒 | 12 → 12 |
| 4レース・64頭の解析＋保存＋レース別品質判定 | 0.884秒 | 0.927秒 | 129 → 129 |

元の全項目・欠損・保存JSON・レース別品質判定は一致。追加の監査情報だけを元の項目の比較から除外し、監査内容は別テストで検証した。実際の学習用ローダーが返すDataFrameも、監査情報の有無で一致することを確認した。

重要な制約:

- 馬情報側の旧保存行は、保存HTMLから得た値で作った検証用データ。2016〜2026年を代表する無作為標本ではない。
- レース側は既存の血統不足が残る4レースで、変更前後とも血統の品質判定は `repair_required`。全品質が合格したという意味ではない。
- 61件の血統HTTP 400は過去に記録された応答コードを再生。元のエラー本文は未保存なので空本文を用いた。保存されたエラーHTMLの完全再現ではない。
- レース側の測定は一覧・カレンダー・日単位の最終監査・外部通信時間・通信間隔待機を含まない。**全体処理の実測ではない。**
- 再利用が成立しないケースでは確認処理が増え、馬情報側は約2.7〜2.9%、レース側は約4.8%遅くなった。これを隠して全体高速化と扱わない。
- 現在の稼働バッチでは測定していない。外部負荷やHTTP制限の発生点を探る試験も行っていない。

根拠: [機械可読の比較結果](../reports/generated/saved-horse-reuse-replay.json)、[再生スクリプト](../scripts/benchmark_saved_horse_reuse.py)。測定中の取得モジュール全体とスクリプトのハッシュを照合済み。

# データ整理・特徴量最適化・並列モデル比較の方針

2026-09-19。提案段階。実装・学習・環境変更は未実施。

## 目的

未来情報を使わない共通の学習データを作り、複数候補を一括開始・資源上限付きで並列実行する。特徴量追加の効果、モデルの種類による効果、計算時間を分けて比較する。選抜モデルを保存するが、使用中モデルは自動変更しない。

## 確認済み環境と制約

- CPU：Ryzen 7 7800X3D、8コア／16スレッド。
- RAM：約32GB。確認時の空きは約11.8GiBであり、全容量を学習へ割り当てられる状態ではない。
- GPU：RTX 4070 Ti SUPER、VRAM 16GB。確認時は約1.8GiB使用中。
- Python環境：LightGBM 4.7.0、Optuna 5.0.0、PyArrow 25.0.1。CatBoost・XGBoost・PyTorchは未導入。
- 現在の学習台帳は `uq_local_retrain_single_active` により同時1件を保証する設計。並列化には実験バッチ内の子ジョブと資源割当の拡張が必要であり、単にボタンを複数回押しても実現しない。
- 現行画面の回帰・ランキングではOptunaをスキップする経路がある。今回の調整を行う場合は、時系列CV対応の実験用探索を明示的に実装し、通常学習への黙った切り替えで成功扱いにしない。
- 既存GPU検出はnvidia-smiの有無だけなので、LightGBMのGPU学習が動くことは未確認。

WindowsのLightGBMではOpenCL版 `device_type=gpu` を先に検証する。CUDA版はWindows非対応であり、GPU版でもCPU側の処理は残る。[公式インストール説明](https://lightgbm.readthedocs.io/en/stable/Installation-Guide.html)

## 第1段階：元データを保全して学習用データを固定

初回の推奨対象は2016年以降のJRA平地。芝・ダートは同一候補に含めても別集計し、地方・ばんえい・障害は削除せず、別実験群として保留する。この対象範囲は実行前に確定する。

1. DBスナップショットとデータセット版・ハッシュを保存する。
2. 未確定・重複・識別や頭数が不整合のレースを除外し、理由を残す。
3. 旧 `prev_race_*` / `prev2_race_*` と派生値を使用しない。対象レースより前のDB履歴から前走・前々走・過去3/5/10走を再生成する。履歴がなければ欠損・不足フラグを保持する。
4. 通算成績も取得時点の現在値を使わず、対象時点までの履歴から計算する。当該レースの結果列は教師値／評価用と入力用で分離する。
5. 会場・芝ダート・クラスなどの表記、欠損トークン、数値型を正規化する。血統の欠損のみを理由に全馬を捨てない。
6. 初回はオッズ・人気とその派生を入力から外す。観測時刻を検証できる市場情報を使うモデルは別実験とする。

合格条件：採用する履歴の対象日との同日・未来参照0件、対象レース結果の入力混入0件、学習と評価のレース重複0件。欠損率・除外件数・期間別件数・取得経路を保存する。

## 第2段階：比較するモデル

全候補で同じ対象レース、日付分割、履歴規則を使う。既存モデルの表示指標は参考にとどめ、安全なデータで作り直したM01を比較基準とする。

| ID | 表示名 | 目的 |
|---|---|---|
| M01 | 速度・基本 | LightGBM回帰。基本条件のみの基準 |
| M02 | 速度・履歴 | M01＋安全な過去走・休養・距離／コース適性 |
| M03 | 速度・拡張 | M02＋血統・騎手・調教師等の安全な過去集計 |
| M04 | 速度・厳選 | M03から改善しない特徴群を削減。軽量性と安定性を検証 |
| M05 | 順位・比較 | 同じ安全な特徴群でLightGBMランキング。順位予測に向くかを検証 |

M01/M02/M03/M05は実行可能な資源枠へ同時投入できる。M04は開発期間の特徴量比較後に作るため依存ジョブとする。「一括開始」は全候補が同じ瞬間に無制限で動く意味ではなく、依存関係を自動管理しながら並列実行する意味とする。

必要なら第2弾でCatBoost回帰を追加し、同じデータでアルゴリズム差を比較する。未導入のため依存関係・モデル保存・推論互換性の検証を別途行う。最初から大量のライブラリを導入する計画にはしない。

## 第3段階：特徴量とパラメータの選定

- 欠損率だけでなく、時点の正当性、分類の揺れ、取得コスト、期間別の安定性を確認する。
- 基本→履歴→拡張の差、および特徴群を外した差で効果を測る。
- SHAPは寄与の説明と問題発見に利用し、重要度上位という理由だけで採用しない。
- 過去の重要度による固定除外を見直し、年齢・斤量等の安全な項目も同じ条件で検証する。
- 補完、カテゴリ変換、特徴量選択、速度偏差の基準はCVの各foldの学習側だけでfitする。
- 初回は固定した小さな探索範囲で全候補を比較し、上位2候補だけ追加調整する。試行数・時間・seed・失敗を記録する。
- fold／Optuna試行／モデルのすべてを入れ子に全並列化しない。並列枠を共通管理する。

## 第4段階：時系列で評価

初期案：学習開始2016年、開発評価2023・2024・2025年、最終試験2026年1月～スナップショット内の直近確定日。件数と過去の評価利用状況を確認して、実行前に固定する。

- 2023年検証は2022年までで学習、2024年検証は2023年まで、2025年検証は2024年まで、という前進型の分割を使用する。
- 全候補は開発期間で比較し、特徴量・パラメータ・評価ルールを固定する。
- 最終期間は基準モデルと選抜候補の最終確認用とし、その成績を見て再調整しない。
- 既存モデルは2026年7月までの学習歴があるので、2026年全体を使った公平な未学習比較の基準にはしない。
- 既に開発判断に利用した期間は未使用とは呼ばない。必要に応じて以後の新しい開催を最終的な前向き検証に残す。
- 評価期間内の先行日の確定結果を翌日以降の履歴に使うかは事前固定する。推奨は実運用に合わせた日次更新で、同日結果は履歴に入れない。

### メイン表示は5項目

| 指標 | 定義・注意 |
|---|---|
| 順位相関 | レース内の予測順位と確定順位の一致度。レース単位で集計 |
| RMSE | 同じ基準で作った速度偏差の予測誤差。ランキングモデルは対象外表示 |
| 1位推奨の勝率 | 予測1位馬が勝った割合。モデルの出力確率とは別 |
| 人気1位との差 | 同一レース集合の1番人気勝率との差をpercentage pointで表示 |
| 回収率 | 事前固定したシミュレーションの払戻総額÷購入総額×100 |

詳細欄：MAE、R²、ランキングのNDCG、検証期間、対象／除外レース数、芝ダート別・年別成績、信頼区間、学習時間、使用メモリ、採用特徴量。平均だけでなく期間ごとのばらつきを確認する。

回収率の初回ルール案は「各対象レースの予測1位へ単勝100円」。確認済み払戻金、取消・返還、同率時の扱いを固定し、実際の購入はしない。払戻金の欠損を0円扱いにせず、評価不能件数・カバー率を併記する。複勝・馬連・馬単・ワイド・三連複・三連単は各券種の確率／購入規則／払戻検証を行うまで未評価とする。最終人気との比較も、事前時点のオッズがあることの証明とは区別する。

選抜は開発期間の順位性能を中心に、勝率・誤差・期間別安定性・計算コストを併せて判断する。回収率の一点最大だけで採用しない。改善の不確実性が大きい場合は「優位性未確認」とし、既定モデルを切り替えない。

## 第5段階：CPU／GPUの資源管理

1. 整理・安全な履歴生成は一度行い、共通の読み取り専用キャッシュを利用する。foldごとにfitが必要な統計は共有キャッシュと分離する。
2. 開発用の同じ代表データ・同じパラメータでCPU/GPUを比較し、GPU学習の成否、精度差、時間、RAM/VRAMのピークを測る。
3. 初期の同時実行はCPU1件＋GPU1件。空きメモリと実測を満たす場合のみCPU2件＋GPU1件へ増やす。GPUも前後処理でCPUを使うためCPU枠を予約する。
4. CPU候補ごとにスレッド上限を設ける。例としてCPU2候補なら各4スレッドを起点にし、GPU側前処理と画面/APIへ余力を残す。
5. GPUはまず同時1候補。VRAMを使い切らず、失敗時は記録した上でCPU再実行へ戻す。GPUを使えなかった実験をGPU実行と表示しない。
6. メモリ不足時は新規開始を待機させ、他アプリを停止したり既存ジョブを強制終了したりしない。

GPUの有利不利はデータ規模等に依存するため、倍速や完了時刻を現時点では断言しない。ベンチマーク後に、前処理を含む全体時間とモデルfitだけの時間を分けて見積もる。[LightGBM公式GPU性能ガイド](https://lightgbm.readthedocs.io/en/stable/GPU-Performance.html)

## 第6段階：既存安全機構を維持した一括実行

- 1つの実験バッチに候補子ジョブを持たせ、子ジョブごとにlease、heartbeat、停止、再開、成果物ハッシュ、実行環境を記録する。
- 現行の単一実行制限を無条件に外さず、実験内の資源枠で制御する。
- データ・特徴量・コード・分割・seed・device・パラメータを全成果物へ紐づける。
- 契約はversion付きで拡張し、試行ごとの採用列・列順・除外列・前処理版を準備時と実行時で一致させる。現在の完全一致チェックを無効化して特徴量の差し替えを通す構成にはしない。
- 各候補は専用プロセス・出力先を持ち、終了時にメモリを回収する。
- 共有されているworkerログ・ローテーションログを試行別に分離し、成果物名にも実験ID・試行IDを持たせる。
- UIを閉じても処理は継続し、再度開くと待機／実行中／完了／失敗と比較結果を確認できる構成にする。
- API再起動時は独立workerのPID・生成時刻・heartbeatを確認する。生存中workerを二重実行したり、停止確認前に資源枠を解放したりしない。
- 候補保存と既定モデルへの昇格を分離する。現在のモデルを上書きしない。
- 実験中は基準モデルを固定する。現在はアクティブ指定読取失敗時に最新モデルへフォールバックするため、候補を通常models領域へ無差別に公開しない。最終採用だけを基準モデルの一致確認と原子的ポインタ切替で行う。

## 完了条件

安全性検査を通ったデータセット、各候補の再現可能な成果物、同条件の比較表、特徴量の寄与説明、CPU/GPU別の実測時間を残す。精度向上は結果で判断し、候補数やGPU利用自体を成果とはしない。

この反映確認は高速化率の実測ではない。全体速度と馬情報の再利用部分の速度は、引き続き分けて評価する。
