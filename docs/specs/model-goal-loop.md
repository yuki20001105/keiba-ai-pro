# KeibaAI model goal-loop

## 固定する目的

2026-10-25追加のデータ品質専用モードは末尾「欠損改善モード」を参照。
以下のモデル探索モードと、収集を許可する境界・完了条件は別である。

**本番を変更せず、欠損診断 → 改善仮説 → 候補学習 → 同条件の時系列比較を実行し、
再計算可能な証拠で採用候補・棄却・判定保留を判断する。**

「必ず精度や回収率を上げる」は完了条件ではない。改善を確認できなくても、
比較実験が正常に終了し、根拠を保存できれば基盤としての目的は達成する。
`verified=true` と `model_improved=true` は別の判定である。

設計参考: [goal-loop 紹介記事](https://qiita.com/aktsmm/items/c61be34e5b7214e346e3)。
記事の完了条件固定・外部検証・Task/Progress Ledger・有限反復を、
KeibaAI のローカル実験向けに実装したもの。外部スキルのコードや文章を同梱していない。

## 実装境界

初期版の入口は `scripts\run_model_goal_loop.py`。既存の隔離実験データ生成、
OS ドライバーロック、SQLite の lease/fencing、ワーカー停止・成果物ハッシュを再利用する。
Next.js/FastAPI の本番経路・認証・モデル登録・既存テーブルは変更しない。

| 機能 | 初期版 |
|---|---|
| 欠損診断 | 開発期間の特徴量、月別・競馬場別欠損、定数・相関、取得原因の不明扱い |
| 改善仮説 | ローカルの決定的ルールで正則化・特徴量グループ除去・学習目標比較・取得調査案を生成 |
| 学習 | CPU 1ワーカー、LightGBM の速度偏差回帰・ランキング・勝敗分類 |
| 探索 | 承認済みの特徴量・探索範囲だけで Optuna |
| 外部検証 | 確定済みキュー結果、ファイルハッシュ、元評価集団から指標を再計算 |
| 可視化 | ローカル `dashboard.html`。欠損、寄与、年別成績、確率信頼度、参考損益 |
| コード・取得改善 | 提案のみ。承認要求を出力し、自己修正や追加取得は実行しない |
| 本番モデルとの比較 | 初期版は同条件で再学習した対照。稼働中モデルの成績とは呼ばない |
| 確率校正 | 未実施を明示。勝敗分類は sigmoid をレース内で正規化するだけ |
| 未知期間・正式購入評価 | 自動では実施しない。既存の承認・受入・昇格基盤に分離 |
| 外部 LLM | 呼び出さない。生データ送信・外部キー設定は不要 |

これは前段の診断・実験自動化リリースであり、承認済み受入契約の充足や、
全体仕様の本番昇格・ホスト済みワークベンチ統合まで完了したことを意味しない。
LLM で提案を拡張する場合も、同じ構造化提案・承認範囲・検証境界を通す必要がある。

## 完了条件

Task Ledger に以下を固定し、後から緩和しない。

1. データ・コード・目的・承認済み設定が一致する。
2. 開発期間だけで診断する。
3. 対照と最低1件の候補を、確定済み成果物から検証できる。
4. 計算上限と試行履歴を保持し、探索の終了を記録している。
5. 同じレース集団から比較指標を再計算できる。
6. 既定モデルポインタと本番受入・購入ポリシーを変更していない。

`verify` は全条件を満たす場合だけ終了コード0。条件未達・予算切れは2、
入力不正・契約不一致・検証エラーは1。AIの説明や自己申告を合否に使わない。

## データ契約

元SQLiteから独立スナップショットを作り、既存の中央平地・完全出走馬集団に限定した
安全特徴量データを生成する。元DBの更新・欠損補完はしない。
対象集団の選択による欠損・成績の偏りは、全取得データの品質と区別する。

- 履歴は `source_race_date < target_race_date`。同日の結果も入力に混ぜない。
- 当該レースの結果・タイム・オッズ・人気・払戻を予測特徴量に使用しない。
- 勝敗・速度の教師データ、参考評価用の結果と特徴量の列を区別する。
- 年ごとの学習は学習開始年から評価年の前年末まで。前処理と速度基準値は学習側だけで適合。
- 各レースは完全な出走馬集団を維持し、候補間で評価対象を変えない。
- 欠損はNaNを保持。前々走は過去2走、過去N走の平均・率は窓内件数、
  同条件・騎手・調教師・血統の統計はそれぞれの観測件数を使って自然欠損を判定する。
  馬IDが必要な特徴量のID不明、件数不明・不正値は原因不明のままにする。
  集計済みの対象集団に履歴がないことは、実際の新馬・全履歴の取得済みを意味しない。
  過去走数があっても上がりタイムがない場合は、自然欠損と断定しない。
- 取得証跡がなければ原因は `unknown`。欠損率から通信・パース失敗と断定しない。
- 既存の完全レース集団には速度結果の存在条件がある。勝敗分類でもこの集団を使い、
  全運用レースへの汎化や欠損レースの品質を保証しない。

標準の開発年は2023〜2025。これらは既存実験で観測済みであり、
**未知の最終テストとは呼ばない**。設定した開発期間より後の評価行を診断・学習に読まない。
スナップショットと特徴量生成には履歴・評価用の保存行を含むが、探索の指標に混ぜない。

## 評価契約

全目標の主比較はレース平均Spearman順位相関。定数スコアのレースは0として数え、
都合の悪いレースを除外しない。速度回帰ではRMSE/MAE、ランキングではNDCGも出力する。
勝敗分類ではレース内正規化した確率からAUC、Log loss、Brier、10区間ECEを出力する。
ランキングや速度のスコアを勝率とは扱わない。

`verify` は予測ファイルを元データのレース・馬番・日付・着順・馬場・市場評価列と照合する。
速度の教師値も学習期間の元データから再計算する。報告された主要指標だけを信用しない。

候補と対照は同じ開催日を同時に再標本化し、順位相関差の95%区間を計算する。
設定した最小改善差、年別非劣化、1位指名的中率の非劣化、区間下限の正値を要求する。
日数不足なら `inconclusive`。これは探索内の記述的な区間であり、
多数の仮説選択によるバイアスを取り除いた未知期間の証明ではない。

参考損益は既存の実験評価と同じ「各レース予測1位へ単勝100円」。
払戻不明があれば全体損益を未計測とする。最終人気による参考比較であり、
購入時点の市場を再現した評価ではない。

**承認済み `phase3n-tansho-flat-v1` の期待値1.2条件付き購入評価とは異なる。**
正式な購入・受入の判断には、既存の `model_acceptance_contract.v1.json`、
時刻付き観測、別途校正、信頼された証拠生成・独立承認を必要とする。
本CLIは `promotion_eligible=false` を固定し、Kellyや購入条件を探索しない。

## 予算・停止

正本は `config\model_goal_loop.v1.json`。準備時に複製して承認ハッシュへ束縛する。
既存の本番受入閾値は書き換えない。

| 設定 | 標準値 |
|---|---:|
| 改善仮説 | 最大3件（承認待ちの取得調査案を含む） |
| 1仮説のOptuna試行 | 最大30 |
| 全学習試行 | 対照を含め最大90 |
| 探索時間 | 初回runから6時間。再開してもリセットしない |
| 改善なしの停止 | 連続2仮説 |
| 同時学習 | CPU 1ワーカー、4スレッド |
| 基本ブースト回数 | 200 |
| 日単位bootstrap | 300回、最低20日 |
| 最小順位相関改善 | 0.001 |
| 許容年別低下 | 0.01 |
| 許容1位的中率低下 | 0.005（0.5ポイント） |

`min_data_in_leaf`、葉数、学習率、L2のみを固定された範囲で探索する。
仮説に指定されたパラメータは固定し、そのほかを探索する。
1試行で複数年を学習するため、試行数とfit回数は異なる。
同じ仕様の再投入は履歴で検出し、実行せずOptuna上で打ち切る。
停止理由は `plan_completed` / `stagnation` / `budget_exhausted` / 明示的エラー。

時間上限は実行中ワーカーにも適用する。終了時の確認・協調停止・所有プロセスの回収には
追加時間がかかる。別のWeb/PythonサービスをPID名検索で停止しない。
取得制限、任意コード実行、予算の自動増額、失敗・期限切れワーカーの自動再投入は行わない。

## 台帳・承認・再開

```text
reports\generated\model-experiments\<campaign>\
  task-ledger.json       目的・完了条件・設定・データ/コード/ポリシーのハッシュ
  approval.json          ローカル実験だけの承認
  run-budget.json        初回run時刻と固定の期限
  progress\              ハッシュ連鎖した進捗イベント
  diagnostics.json       開発期間の欠損・相関・品質診断
  proposals.json         有限の改善案
  attempts\              Optuna試行と実行payload
  decisions\             比較結果と採否理由
  approval-requests\     コード・取得調査の承認待ち（未実行）
  experiment.sqlite3     既存のlease/fencing付き学習キュー
  optuna.sqlite3         探索履歴
  trials\                モデル、予測、寄与、ハッシュ、ログ
  verification.json      独立した再計算による合否
  dashboard.html         ローカルの可視化
```

承認は正確なTask Ledgerのハッシュに束縛する。変更された条件での再開は拒否する。
このローカル承認を、本番ワークベンチの二者承認や昇格権限の代用にしない。

完了済み成果物は再検証して利用する。途中の `running` / `unknown` / `failed` は
調査が必要で、別IDや台帳編集による迂回を認めない。別実験の未解決キューも起動を阻止する。
キャンセル後や予算途中停止後は、`status`・ログ・ワーカー停止を確認する。
安全に完了していない学習を自動で再投入しない。

各試行で独立再計算したレース別記録は、同じrun内の比較で再利用する。
完了時の `verify` は全成果物を改めて検証し、途中のファイル変更を見逃さない。
実行中にコードを修正せず、終了後に新Campaignのソース契約へ変更を固定する。

## PowerShellでの操作

リポジトリルートから実行する。新規IDを使用し、同じ場所を他の実験で再利用しない。
`prepare` はローカルDBの複製・特徴量生成を行い、時間と容量を使用する。
`run` は実際の学習を行う。どちらもネット取得・既定モデル変更は行わない。

```powershell
$campaign = 'reports\generated\model-experiments\keiba-goal-01'
$python = '.\python-api\.venv\Scripts\python.exe'
$entry = '.\scripts\run_model_goal_loop.py'

& $python $entry prepare --root $campaign
# task-ledger.json、diagnostics.json、proposals.jsonを確認してから承認する。
& $python $entry approve --root $campaign --actor local-operator
& $python $entry run --root $campaign
& $python $entry verify --root $campaign
& $python $entry status --root $campaign
# 停止が必要な場合のみ:
& $python $entry cancel --root $campaign
```

別の設定は `prepare --config <JSON>`、別の保存DBは `prepare --source <SQLite>`。
準備後は設定を書き換えず、新Campaignとして作り直す。

## 段階的な拡張

### 凍結済みCampaignの資金配分・品質分析

`scripts\analyze_goal_campaign.py` は完了済みランキング候補を再検証し、
別ディレクトリに年別損益・欠損・レース別研究額を保存する。元Campaignを更新しない。
既存の本番受入・購入契約とは別の研究シナリオであり、実購入額は常に0。

- 年間予算は延べ購入額の上限。初期資金や使い切る目標とは区別する。
- 年間1,000万円の等額換算は参考値で、端数・市場影響を再現した事前配分ではない。
- 固定額とスコア差の3段階配分は、予定対象数・固定閾値・当年既支出から金額を決める。
  将来の年間レース数や払戻で配分を正規化しない。上限超過は防止する。
- スコア差は校正済み勝率・期待値ではなく、Kellyを実行しない。
- 購入対象に払戻不明レースがあれば、その年の全体損益・回収率・ドローダウンは未計測。
- ドローダウンは日次精算ベース。レース時刻順・資金残高の実運用再現とは呼ばない。
- 品質は元集団・選択済み集団・年別に母集団を明示し、自然欠損と原因不明を分ける。
- 取得品質台帳・公式開催全件照合・予測時点のフィールド取得時刻は別々に確認する。

### 未実装の運用拡張

任意のコード・取得改善提案の自動実行、独立した確率校正、稼働中モデルとの公平な比較、
既存Adminワークベンチへの表示、未知期間・正式購入ルールでの観測を別段階で追加する。
CatBoost/XGBoostはLightGBM契約の流用ではなく、個別の推論・保存契約が必要。
いずれも既存の不変条件や本番受入基準を緩和しない。

## 欠損改善モード

明示的な依頼・許可の下で実行する `repair-missingness / verify-missingness` を追加する。
モデル探索モードの自律収集権限を広げるものではない。実装は
`python-api\scraping\missingness_goal.py`、入口は同じ `scripts\run_model_goal_loop.py`。

### 固定契約

- 元Campaignの凍結DB・既存データセットは読み取り専用。元のソース契約を新コードで
  再承認せず、**新しいデータ品質契約**の対照入力としてバイトハッシュで結び付ける。
- 新しい出力は `reports\generated\data-quality\feature-gap` の直下だけに作る。
  元Campaignの台帳・DB・予測や本番主DB・モデルを更新しない。
- 2016〜2025年、同一行・同一レースで72特徴量の欠損を比較する。
- 固定2反復: 明示された保存クラス条件の復元、厳密な血統整合補完。
- 第1反復はクラス以外、第2反復は父・母父の6統計特徴量以外の値が不変であることを要求する。
- 旧500/1000/1600万下と現1/2/3勝クラスの明示条件を読む。既知値の上書き、
  名称だけによるクラス推定、矛盾条件からの選択はしない。
- 血統修復は既存 `pedigree_gap_repair` の出典照合・条件付き更新・ジャーナルを
  **研究用DBコピー**にだけ適用する。既存修復契約の対象期間は
  2016-01-01〜2026-10-16であり、評価集団や全凍結DBの期間とは区別する。
- 別の明示フラグ `--probe-pedigree` は保存証拠なしの最大20頭、
  `--probe-clock` は追跡できる元レースの最大1件だけ公開ページを確認する。
  血統は連続3件進展なしでも停止する。無制限の再試行・自動継続はしない。
- 通信は共通fetch制御を使い、最小2秒、個々の要求は再試行・リダイレクトなし。
  制限応答で停止し、ブロック解除や別ホストへの回避をしない。
  共有HTTPキャッシュの通常の更新は許可し、主DBへの補完とは区別する。
- 現在取得した血統は要求先・canonicalの馬ID、血統テーブル、既存の厳密な名前規則を
  満たすものだけ研究用キャッシュへ入れる。生応答・ハッシュ・拒否理由も保存する。
  国コード除去や推測した翻訳同定を行わない。
- 時計は既存 `parse_last3f_evidence` で日付・全出走馬を確認する。
  調査用観測であり、過去の公開時刻や欠損値そのものを書き換えない。
- 過去件数不足は、選択した履歴に対する不足として扱う。本当の初出走、
  公式履歴の網羅、取得不能と同一視しない。
- `verified` は入力・コード・許可差分・修復行・同一集団・保護対象の検証結果。
  `zero_missingness_goal_met` は別に判定し、未達なら終了コード2にする。
  これは精度・校正・回収率・未知期間評価や本番受入ではない。

### 証拠と実行済み結果

新しい `task-ledger.json`、`progress.jsonl`、修復計画・ジャーナル、
`artifacts.json`、`verification.json` を保存する。
`verify-missingness` は通信せず、欠損数、出典付き変更、行の不変性を再検算する。
ソース変更後は旧契約の再検証を拒否する。再実行は新ID・新契約とし、
同じ取得対象を繰り返しただけで追加改善したと扱わない。

## 研究専用の目的変数比較プロファイル

`scripts\run_target_goal_loop.py` は `keiba-target-goal-loop-v1` の別プロファイル。
既存の起動スクリプト・凍結成果物・CPU 1 worker契約は変更しない。
共通のOSドライバーロックと未解決実験チェックを使用する。

- 固定目的は、校正済み勝率のレース平均NLLを改善し、Top1・順位相関を維持すること。
- 同じ読み取り専用SQLiteスナップショット、課金・現在結果・市場情報を含まない
  46特徴量、完全な中央平地レース・単独勝ち馬の共通集合で比較する。
- 6方式は現行速度偏差、同じ教師値のレース均等重み対照、過去365日条件補正、
  レース内相対速度、勝敗二値、上位3着重視LambdaRank。異単位RMSEで順位付けしない。
- 条件補正は `log(距離/秒)` を使用。各過去レースの総重みを1にする。
  `対象日-365日 <= 履歴日 < 対象日` の芝・ダート別距離曲線を親基準とし、
  芝ダ・距離・場・馬場・天候の細分類を `W/(W+20)` で縮約する。
  異なる芝ダ・距離を一律の全体平均へ切り替えず、親30レース相当未満は未定義。
  log速度尺度の下限は0.005、教師値は±5に制限。クラスの能力差は一律除去しない。
- 開発評価は2023・2024・2025年6月まで。各foldは2017年以降の前々年末までTRAIN、
  前年CAL。最終TRAINは2017年～2025年6月、CALは選定に使わない2025年7～12月。
  2026年は既に観測された履歴の再評価であり、未知の将来テストとは呼ばない。
- 固定2プリセット、開発36学習＋選定済み対照2学習の38件、上限40件・3600秒。
  最大2プロセス×各2スレッド。親が期限・4GiB残余RAMを監視し、失敗時は未投入を
  取り消して所有PIDだけ停止する。OSによるRAM専有を保証するものではない。
- `prepare` 後のTask Ledgerハッシュに `approve --actor --task-sha256` を結ぶ。
  実行済み・失敗・unknownを自動再投入しない。同一完了runは再学習せず再検証する。
- 開発選定を先に凍結し、選定済み対照だけ後段比較する。開発・後段とも
  NLL改善0.005以上、開催日単位95%区間下限>0、20日以上、年別を含む
  Top1低下0.005以内・順位相関低下0.01以内を要求する。未達なら現行維持。
- `verify` はスナップショットから共通集合・特徴量・教師を再構築し、38モデルの
  TRAIN基準・カテゴリ辞書・CAL係数・馬キー付き予測・指標・選定・採否を再検算する。
  改善未達でも整合検証成功の終了コードは0。採否は `decision` と区別する。
- 本番DB・既定モデル・購入条件・本番モデル登録には接続しない。
  研究採用候補でも `promotion_eligible=false` を維持する。

## 展開予測の深掘り研究モード

`scripts\run_pace_research.py` は `pace-research-v2` の独立プロファイル。
上記の各モードの目的・予算・既存成果物は変更しない。
既存のOSドライバーロックとSQLite lease/fencingを再利用する。

- 固定スナップショットと検証済みラップを再利用し、新規取得・本番DB更新を行わない。
  現在の準備元は `reports\generated\pace-stack\20261114-v1`。
  検証済みキャッシュ・スナップショット・出典の不一致は再生成で隠さず拒否する。
- 開発は2022/2023/2024の3fold。各TRAINは2016年から前々年末、前年CAL、
  対象年VALID。展開のTRAIN入力は過去年だけで学習したヘッドの予測を使う。
- 勝率NLLの直接目的、46/80/90の対照、文脈グループ除去、ペース/位置分離、
  条件階層化、競合統計、交互作用、固定比率合成を有限メニューで比較する。
  次の補正・正則化候補は開発指標から選ぶ。任意コードの自己修正は行わない。
- 主指標は年を等重みにしたレース平均NLL。改善幅0.001以上、年別NLL悪化0.005以内、
  Brier悪化0.002以内、Top1低下0.005以内を選定基準にする。
  数値上の最小と、追加特徴量の優位性が実証されたことは区別する。
- 最大10ステップ・24構成・360 fit予約・6時間。1ワーカー・2スレッド。
  fit予約は各LightGBM、温度校正、速度基準、展開条件閾値を含む。
  3ステップ連続で所定の改善幅がなければ停止する。
- 完了済みの同一試行だけをハッシュ検証して再利用する。
  失敗・unknown・未確定ワーカーは自動で再投入しない。再開時も予算をリセットしない。
- `selection.json`を凍結後、2016–2024 TRAIN・2025 CAL・2026確認を行う。
  2026は既知期間であり、未知期間の採用検証や回収率評価とは呼ばない。
- `verify`は保存予測を元評価集団に照合し、別実装のNLL/Brier/ECEを再計算する。
  全確認スコアを再実行し、当該着順・時計・通過順位の注入が無視されること、
  スナップショット・本番モデル本体・ポインタ・購入ポリシーのSHA一致を確認する。
  `verified`、`model_improved`、`production_eligible`を別の判定にする。
- `analyze_pace_research.py`は検証済み成果物の事後分析・日本語レポート・
  外部通信なしのHTMLグラフを生成する。事後分析で選定を変更しない。

## AIエージェントによる10サイクル研究

`scripts\run_agent_pace_research.py` は独立した `agent-pace-research-v3`。
v2の停滞終了・台帳・成果物は変更しない。AIが前回の開発結果を読み、
仮説と次の3候補を提案する。エンジンが許可範囲とハッシュを検査して学習する。
単なる固定グリッドをAIの考察と呼ばない。

- **成功した10サイクル・新規30構成**を実行する。停滞では終了しない。
  安全性・整合性違反、失敗/unknownワーカー、予算超過では停止し、未完了と報告する。
- 6時間（AI判断時間を含む）・240 fit予約・1ワーカー・CPU2スレッド。
  LightGBM、温度校正、追加ヘッドの条件閾値も予約に含む。
  再開で開始時刻・期限・上限を変更しない。
- 検証済みv2データ・モデル学習ソース・ヘッドの出典とハッシュを確認して再利用する。
  再利用した学習を新規fit件数として数えない。過去成果物を上書きしない。
- 開発は2022/2023/2024の等重みレース平均NLL。
  **強い対照 `win80`** に対し、平均NLL改善0.001以上、
  年別NLL悪化0.005以内・Brier悪化0.001以内・Top1低下0.005以内、
  温度校正の境界到達なしを候補の条件とする。
- 適格候補の数値上の最良からNLL差0.001以内では、特徴量数、平均Brier、
  平均NLL、IDの順で選ぶ。対照もその帯に入る場合は比較に含める。
  数値上の最小と、単純性を考慮した選定モデルは区別して保存する。
- 学習目的は勝率NLL。必須46特徴量と既存の文脈グループ、
  競合統計、予測ペース/位置、許可済み交互作用を比較する。
  反復数120/200/300/450/600、葉7/15/31/63、葉最小件数30/60/120/240、
  L2=1/5/20/50だけを許可する。任意列・コード自己修正・重複学習は禁止。
- AIに渡すコンテキストは開発指標・既試行仕様・過去の判断だけ。
  各提案を対応するコンテキストSHAと結び、提案・評価・選定を改変検知付きで保存する。
  初回に10件の提案を作り置きせず、毎回の結果から次を決める。
- 10回終了後に選定を凍結してから、2024年末までTRAIN・2025年CAL・
  2026年確認を行う。確認結果を使って選び直さない。既知の遡及比較であり、
  未知の将来検証・回収率改善の証明ではない。
- `verify` は全新規開発90fold、再利用対照、確認の予測・指標・モデルを
  再実行/再計算し、当該結果の注入無効、予算、出典、順序、購入条件と本番不変を確認する。
  `verified`、`model_improved`、`production_eligible=false` は別の判定。

再実行用エージェントは `.github\agents\pace-research-controller.agent.md`。
Copilot CLIで `/agent pace-research-controller` を選び、新しい研究IDで10回の実行を指示する。
既存の完了研究を再投入しない。低レベル操作は次の順序:

```powershell
$run = "reports\generated\model-experiments\pace-agent-new"
.\python-api\.venv\Scripts\python.exe -X utf8 scripts\run_agent_pace_research.py prepare --root $run
.\python-api\.venv\Scripts\python.exe -X utf8 scripts\run_agent_pace_research.py approve --root $run
# AIがcontextの結果を読んでproposalを作成し、各回admit→cycleを実行する。
.\python-api\.venv\Scripts\python.exe -X utf8 scripts\run_agent_pace_research.py context --root $run
.\python-api\.venv\Scripts\python.exe -X utf8 scripts\run_agent_pace_research.py admit --root $run --proposal <proposal.json>
.\python-api\.venv\Scripts\python.exe -X utf8 scripts\run_agent_pace_research.py cycle --root $run --cycle 1
# 同じ手順で10回の実評価後のみ:
.\python-api\.venv\Scripts\python.exe -X utf8 scripts\run_agent_pace_research.py finalize --root $run
.\python-api\.venv\Scripts\python.exe -X utf8 scripts\run_agent_pace_research.py verify --root $run
.\python-api\.venv\Scripts\python.exe -X utf8 scripts\analyze_agent_pace_research.py --root $run --report docs\reports\pace_agent_new.md
```
