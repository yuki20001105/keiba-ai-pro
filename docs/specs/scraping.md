# スクレイピング仕様書（Scraping Spec）

> **対象ファイル**: `python-api/scraping/jobs.py`, `race.py`, `horse.py`, `storage.py`, `constants.py`  
> **参照**: [SYSTEM.md](./SYSTEM.md) — INV-07（インターバル）、INV-08（認証）

## 1. Requirement（満たすべき条件）

| ID | 条件 |
|---|---|
| R-SC-01 | システムは netkeiba.com からレース・馬データを自動取得する |
| R-SC-02 | システムは取得済み日付をスキップし、再実行時に再開できる |
| R-SC-03 | システムは各ページリクエスト間に最低 1 秒のインターバルを設ける |
| R-SC-04 | システムは HTTP 429 時に全 netkeiba 通信を共有休止し、Retry-After より早く再開しない |
| R-SC-05 | システムは取得データを `keiba_ultimate.db` に保存する |
| R-SC-06 | システムは進捗（done/total）をポーリングで返す |
| R-SC-07 | システムは過去 30 日超のデータはカレンダーで開催日を絞り込む |

## 2. Specification（仕様）

### 2-1. エンドポイント

| メソッド | パス | 説明 |
|---|---|---|
| `POST` | `/api/scrape/start` | スクレイプジョブを開始し `job_id` を即時返却 |
| `POST` | `/api/scrape/cancel/{job_id}` | 所有者Adminが停止要求を永続化し、安全な処理境界で個別jobを停止 |
| `GET` | `/api/scrape/status/{job_id}` | 進捗を返す（ポーリング用） |
| `GET` | `/api/scrape/jobs` | 全ジョブ一覧 |
| `DELETE` | `/api/scrape/jobs/{job_id}` | ジョブ削除 |

### 2-2. リクエスト

```json
POST /api/scrape/start
{
  "start_date": "20260101",   // YYYYMMDD
  "end_date":   "20260413",   // YYYYMMDD
  "force_rescrape": false     // true = 日付と血統・過去成績の出典を再検査し、不足・未検証レースを修復
}
```

### 2-3. レスポンス（status）

```json
{
  "job_id": "uuid-string",
  "status": "queued | running | cancelling | cancelled | completed | error",
  "progress": {
    "done": 5,
    "total": 12,
    "message": "5/12日処理済み / 40レース保存",
    "saved_races": 40,
    "saved_horses": 480
  }
}
```

### 2-4. 予測時の実オッズ更新

単一・一括予測は `data_refresh="saved_db", refresh_odds=true` を明示指定できる。
特徴量・馬履歴・モデルは保存済みのまま計算し、推論後に単勝実オッズのJSON APIだけを取得する。
予測レスポンスキャッシュ・HTTPキャッシュを使わず、全体60秒以内、既存の共有通信制御を維持する。
この価格更新はレース・履歴DBを書き換えない。通常の予測ログ・成績記録とは分離する。
UIは `live_odds_refresh=true` の能力確認ができない旧APIへの予測送信を拒否する。

取得時刻・本文ハッシュ・レースID・馬番・価格を結び付けた証跡を購入判定に渡す。
`middle` は実オッズ、`result` は締切後の確定値として区別し、`yoso` の予想オッズは不使用。
失敗・欠落・非有限値はnullとし、以前のDB価格で穴埋めしない。過去レースは通信更新せず保存値を表示する。
レスポンスの `odds_refresh` に取得状態とUTC取得時刻を返し、UIは日本時間で表示する。
検証済み確率の期待値は確率×取得価格。勝率・入力が未検証なら購入条件は緩和せず、
表示用の参考比率×実オッズを「参考指数」と明記し、期待値・購入根拠として扱わない。

## 3. 処理フロー（Process Flow）

```
POST /api/scrape/start
  ↓ job_id 即時返却（バックグラウンド実行）
  ↓
[前処理A] 過去 30 日超 → カレンダーから開催日を取得して日付を絞り込む
[前処理B] SQLite の完了・品質台帳で再開対象を確定
  ↓
[日付ループ] dates[] を 1 件ずつ処理
  ├─ 品質合格済み → スキップ
  ├─ 日付一覧 / 検証済み月別索引 → race_id[] 取得
  │    └─ 空応答・400 だけでは開催なしと確定しない
  ├─ [レースループ] 不足・品質未達レースのみ処理
  │    ├─ 30 日超の過去: 有効な保存 HTML を再解析、品質不足なら再通信
  │    └─ 直近: 従来どおりレース本体を新鮮な応答で取得
  ├─ 馬情報・血統を補完（出典・期限・パーサー版が一致する解析結果を再利用）
  ├─ 品質検査 → _save_race_sqlite_only() → 品質台帳・完了記録
  └─ 停止要求があれば、一貫した保存境界で終了

各実通信は共通制御器を通す（カレンダー・オッズ・ブラウザ経路を含む）。
429 → 共有待機 / 401・403・制限 HTML → 自動通信停止。

カレンダー解析は `scraping/calendar.py` に分離し、通常ジョブとforward経路で共有する。
対象の選択年・月と、当月の全日セル・中央競馬場名を検証してから開催日を返す。
ページ全体の `kaisai_date` 文字列や翌月のナビゲーションリンクだけでは開催を確定しない。
通信失敗・年月不一致・日セル欠落・未知の競馬場は未検証として日付別照合へ戻す。
開催日リンクがある日セルで会場表示を認識できない場合も、開催なしではなく未検証とする。
全日セルの照合を通った開催0日と、取得・解析失敗は区別する。
元の応答バイト列を解析し、文字コード宣言を残したHTMLの再エンコードで会場名を壊さない。
このカレンダーはJRAの予定だけを表し、地方開催なしや過去発走前の取得時刻の証明ではない。
既存保存日との突合・直近日再確認・中央専用/全会場の完了台帳ルールは変更しない。
```

### 3-1. 通常取得の過去成績と修復モード

フロントエンドの修復モードは明示的に選択した場合だけ `force_rescrape=true` を送る。
通常の既定値false、既存の所有者確認・承認lock・停止条件は変更しない。
結果が保存済みでも、血統が不足、または中央馬の過去成績の出典・対象日・全件数照合が未確認なら、
修復モードではそのレースを再検査する。全期間一括取得が品質合格したという意味ではない。

通常取得ジョブ内の中央馬は、現行の公開プロフィールから、必要に応じて
`horse/ajax_horse_results.html` の公開成績表を共通通信制御経由で取得する。
馬IDのcanonical照合、成功したAjax応答、日付列・降順を確認し、
**対象日より前の行だけ**を直近成績欄に使用する。当日および未来の行は除外する。
解析キャッシュは対象日とパーサー版、プロフィール・Ajaxの応答版で区別する。

`_career_history_source` に対象日・参照先・応答版・表示件数・対象日前件数・除外件数・
公開通算件数との一致を記録する。不一致・解析失敗は未解決として残し、取得失敗を0走と推定しない。
通算出走数との照合では、成績表に残る明示的な出走取消・除外行を出走数へ加えない。
空欄の着順は取消と推定せず、過去の出走状態不明として残す。
`strictly_prior_race_inventory` に対象日前のレースID・日付・中央/対象外区分・出走状態を保存する。
リンク不明・重複・年不一致を検査し、旧版の履歴記録や未確定クラスも修復モードで再検査する。
`prior_results_imported=false` は、この一覧が過去レース結果のDB保存を意味しないことを表す。
プロフィールの直近2走だけでは学習用履歴は完成しない。
結果として不足する過去走は、元の結果ページで全馬・日付・着順・時計を照合してから別途取得・保存する。
完全照合した対象日付き履歴で既存の直近成績を更新する場合は、古い現在プロフィール由来の
当日・未来の値を引き継がない。真の初出走では直近成績が空になるが、これは取得失敗ではない。
通算成績は取得時点のプロフィール値であり、過去発走前の利用可能性を証明しない。

中央馬の専用血統ページを追加取得する場合は、子馬ID・親リンクID・世代位置を照合する。
外国馬の英数字IDや国名付き表記は保持し、既知の血統と競合したら補完しない。
稼働予測経路・凍結済み研究集団・学習時の欠損補完規則は、この通常取得向け変更では切り替えない。
生データ取得ではモデル入力用の推定値を実測値として書き込まない。

既存の正常走が、他馬の着順欠落のため未検証の部分結果として除外されている場合は、
欠落馬を取消・除外と推測しない。全馬の結果ページで明示された状態を復元し、
通常の品質判定を通った結果にだけ完了台帳を記録する。
品質・修復台帳のDB接続は処理終了時に明示的に閉じ、修復のチェックポイントを妨げるロックを残さない。

### 3-2. 全項目の欠損監査・研究用履歴修復

欠損の監査は凍結したレース・馬・日付・行順と特徴量契約を固定して行う。
保存JSONのキー不在、観測値のnull・不正値、利用可能履歴の不足、推定済みモデル入力は別集計とする。
保存履歴0だけでは公開元での初出走としない。公開件数・対象日前の出走状態・リンクを確認し、
根拠のないセルは未照合のまま記録する。143項目のJSONキー不在合計を取得失敗数へ変換しない。

`scripts/audit_acquisition_adequacy.py` は全安全特徴量の欠損セルと全保存項目を監査し、
公開過去リンクを、既存利用履歴・対象外・初期履歴契約外・状態不明・元結果要照合に分ける。
`scripts/verify_acquisition_adequacy.py` は全欠損セルの所属・理由・根拠・修復対象と
保存項目のSQL集計を再検証する。検査標本の公開初出走率を全件へ外挿しない。

`scripts/repair_linked_history.py` は研究用の別出力で元結果を照合する。
公開リンク日と保存日・対象日の一致、公開された距離・馬場、全馬の識別、
既存の正常な着順・時計の原文一致を必須とする。
曖昧な空着順を取消とせず、明示された非完走状態だけを復元し、通常の全結果品質判定を通す。
別DBへ変更前画像付きで保存・独立照合してから全期間へ再適用する。
この経路の追加は、通常取得ジョブ・フロントエンドで全過去結果の自動保存を実装した意味ではない。

別の公開血統出典を使う場合は、子馬の馬名・生日・生産者、親リンクと世代位置を照合する。
提供元の馬IDは別名前空間として保ち、国名付き表示を勝手に除去しない。
名前・親IDの対応が未確認なら観測の保管にとどめ、既存の親別モデル集計へ自動投入しない。
現在の公開値の確認を、過去発走前の取得時刻の証明として扱わない。

### 3-3. 必要な公開観測だけを取得する経路

公開観測と、観測から計算するモデル特徴量を分離する。勝率・平均速度・条件別平均・
欠損補間値を公開元から取得した値として保存しない。
対象日前の結果だけで計算し、統計が未定義なら原観測の取得不備と区別する。

| 必要な情報 | 取得元・用途 |
|---|---|
| レース・馬・騎手・調教師の識別、距離、馬場、クラス、斤量等 | 結果・出馬表の本体。発走前/結果の役割を分離 |
| 着順、非完走状態、時計、上り、馬体重等 | 結果本体。教師ラベルと対象日前の履歴に使用。対象レースの結果は予測へ入れない |
| 公式払戻 | 同じ結果応答から取得。実績損益に必要な観測で、最終オッズから代用しない |
| 対象日前の公開成績・結果リンク | 子馬IDを確認したプロフィール。表がなければ公開Ajaxを追加 |
| 父・母・母父の名前と提供元ID | 子馬・世代位置・親リンクを検証した専用血統応答を再利用 |
| 購入時刻の市場 | 別の時刻付き市場観測。過去結果の最終オッズを購入時点の観測としない |

`historical-jra-required-public-v1` は通常取得ジョブ内の**30日超の過去・中央馬**だけに適用する。
主経路はレース本体 → 必要な公開成績 → 必要な血統である。
プロフィールから追加保存するのは対象日前の互換用直近成績と出典・リンク台帳だけで、
現在の通算成績・通算賞金・所有者・生産地・毛色補助ページは過去学習用に追加保存しない。
公開通算件数は成績表の網羅性確認用メタデータにだけ残す。既存の保存値は一括削除しない。
別登録簿との子馬照合に生日・生産者が必要な場合は、その識別根拠として別途扱う。

実装は `required_public_inputs.py`。通常ジョブのコンテキストからだけ有効化する。
直近・当日・将来、直接の予測呼び出し、地方馬および稼働中の凍結研究取得器は従来経路を維持する。
血統の解析再利用は子馬ID・パーサー版・HTTP応答版を照合し、名前だけの旧キャッシュで
親IDが確認できたことにしない。既存の名前・国名表記・IDと競合した家族は補完しない。
保存側でも既存の親別名・IDとの競合を検査し、明示的な修復エラーとする。
現在プロフィールとAjaxの応答は6時間以内の版を使用し、旧7日キャッシュは必要な応答だけ更新する。
HTML解析は既存の2ワーカー上限を保持する。

成績の0行は公開件数・表・子馬の照合結果とともに記録し、通信失敗を0走としない。
プロフィール・追加Ajaxの通信情報は `_career_history_source` の `profile_fetch`・
`history_fetch`、血統は `_pedigree_source.fetch` に記録する。
各記録はHTTP状態・通信元・試行回数・元の通信エラーを保持し、既存の役割別エラーコードは維持する。
HTTP状態0でも `timeout`・`total-timeout` 等の理由を失わず、公開データ不存在とは判定しない。
HTTP成功後の解析拒否は通信エラーと区別し、通信情報を自動再試行の許可として使わない。
血統の解析再利用時は、元の応答取得情報を保持し、再利用を新しい通信と扱わない。
地方・海外・初期履歴契約外は取得失敗とも未経験とも扱わない。
`prior_results_imported=false` を維持し、公開の結果リンク取得を全結果DB取り込み完了にしない。
必要な過去結果の保存とモデル受入は引き続き別の品質・範囲・実行承認を要する。
この限定取得は全72項目のNaN 0を保証せず、新しいモデル補間規則を導入しない。

API健康応答は取得方式の版・対象範囲・通算値非入力・結果自動取り込み未実装を返す。
画面は安全制御に加え、この版と範囲の一致を確認して新規取得を許可する。
古いAPIでは新規実行を停止し、既存ジョブの監視・停止・所有者確認・承認lockは維持する。
この変更は実行権限・DB書き込みguard・本番モデルの自動有効化ではない。

## 4. インターバル仕様（Interval Spec）

### 予測用の軽量一覧取得

予測画面は通常のローカルジョブに `horse_details="cached_only"` を明示する。
この値も所有者付きの要求ハッシュ・再開要求へ保存する。旧要求のハッシュは変更しない。
サーバーバッチ・デプロイ環境ではこの新しいモードを受け付けない。
当日・未来の出馬表と時刻付きオッズは通常どおり取得し、馬プロフィール・Ajax成績・
血統の追加通信はしない。既存の馬ID別血統キャッシュだけ再利用し、欠損を0走と推定しない。
過去日になった対象は再開時も完全取得へ戻る。学習用の通常取得・修復は既定の完全取得を維持する。
公開APIの `prediction_card_policy_version="prediction-card-cached-v1"` がない場合、
画面は遅い旧ジョブへ黙ってフォールバックせず、再起動を案内する。

ソース検証済みDB共有モデルの当日・未来の再予測も、完全な血統キャッシュがある馬は
プロフィールを再取得せず、血統が不足する馬だけ従来の補助取得を実行する。
履歴特徴量は既存の対象日前DB履歴から計算し、学習・特徴量契約・未来情報除外は変更しない。
旧モデル・過去の結果再取得は完全取得のまま。出馬表・オッズの鮮度・原子的保存と、
通信の3秒下限・単一発行枠・制限時停止は維持する。
軽量行には `_horse_details_deferred=true` を保存する。旧モデルへ切り替えた場合は
完全取得を要求し、保存DBのみの指定なら通信せず409を返す。履歴の出典が検証済み、または
プロフィール・前走情報を取得した行では解除する。取得失敗・血統のみの行では解除せず、
更新・保存後にも保留が残る場合は旧モデルの計算を409で拒否する。新馬の正当な0戦は取得失敗と区別する。
このフラグは履歴の完全性の証明ではなく、既存の品質・出典検査を代替しない。
画面の能力確認は投入先と同じスクレイプAPIの健康応答を使用し、別のML APIで代用しない。

> **INV-07 より**: netkeiba 全体のリクエスト開始間隔は最低 **1.0 秒**、同時通信は **1**。

`request_pacing.py` の SQLite lease によってプロセス間でも発行枠を共有する。
初期 2 秒。ページ種別ごとの正常応答が 50 件以上かつ 120 秒以上安定すると 10% ずつ短縮する。
応答遅延・5xx・タイムアウトでは減速する。キャッシュ処理に日付・レース単位の固定待機を追加しない。
制御 DB の故障時に無制御の通信へフォールバックしない。

## 5. リトライ仕様（Retry Spec）

`fetch_pipeline.py` が再試行を管理し、各試行・リダイレクトも共有発行枠を取得する。

- 429: `Retry-After`（秒数・HTTP 日時）と内部 5 分以上の指数待機の長い方を共有。再起動でも期限を維持。
- 401・403・制限 HTML: `FetchAccessBlocked` で停止。他サブドメインへの切替・自動再試行は行わない。
- 400: 開催なしや互換性問題と即断しない。別形式で妥当な結果を取得できた場合のみ、ページ種別の参照先を 24 時間記憶。
- 5xx・タイムアウト: 上限付き再試行と減速。成功しなければ品質不足として残し、完了にしない。

## 6. データ保存仕様（Storage Spec）

### 6-1. 保存先

| テーブル | 内容 | キー |
|---|---|---|
| `races_ultimate` | レース基本情報（JSON） | `race_id` |
| `race_results_ultimate` | 馬ごとの結果（JSON） | `race_id` + `horse_number` |
| `scraped_dates` | 取得済み日付 | `date` |
| `pedigree_cache` | 血統キャッシュ | `horse_id` |

### 6-2. 保存条件

```
While スクレイプ済みレースを保存する,
when race_data.horses が空のとき,
the system shall 保存をスキップしてログに警告を記録する。

While スクレイプ済みレースを保存する,
when distance = 0 のとき,
the system shall _invalid_distance フラグを true にして保存する（予測時に除外される）。
```

## 7. Cloudflare ブロック対応

```
While ページ本文を取得する,
when Cloudflare ブロック HTML を検知したとき（is_cloudflare_block() = true）,
the system shall netkeiba 全体の停止理由を永続化し、以降の自動通信を停止する。
the system shall 保存済みの途中成果を保持し、ジョブを error として理由を表示する。
```

解除は運用者が原因を確認してから行う。再起動・プロキシ切替による自動回避は行わない。

## 8. 禁止事項まとめ（Do NOT）

| # | 禁止内容 |
|---|---|
| DN-01 | インターバルを 1.0 秒未満に変更すること |
| DN-02 | `force_rescrape=true` をデフォルトにすること |
| DN-03 | 複数日付を並列（asyncio.gather で複数日）に処理すること |
| DN-04 | `scraped_dates` テーブルを削除・スキップするリロジックを追加すること |
| DN-05 | 401・403・制限画面を無視し、再試行や別ホストへの切替で通信を続けること |
